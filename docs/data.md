Snapshot checked 21 November 2026. Publication/evaluation dates differ and are retained where reported. This app links published findings; it has not independently rerun the evaluations.

Source terms were checked on 18 November 2026. ## Pricing

23 models have official standard API token rates: seven OpenAI, five Anthropic, six Google, two DeepSeek and three xAI. Rates are USD per million tokens; they do not imply a per-project cost. Long-context tiers and DeepSeek peak/off-peak conditions are recorded. Gemini Carbon/Argon promotional rates and the announced 1 December change are retained.

98 model identities cover these price records plus benchmark-only and report-only models, including older releases and image models. The remaining identities have no verified price record in this snapshot. Missing values are never filled by analogy. Provider positioning is labelled as a provider description.

## Identity and normalization

Each model's status (current, previous or preview) feeds the filter bar's "Current models only". Priced models take it from `research/pricing.json` and the others from `research/model-status.json`, which gives a reason for each; a model is previous when a newer model of its line is in the data or its provider names a replacement. Ten models, mostly image models, have no status because the data does not settle it.

The build script joins exact reviewed names and a small explicit spelling-alias table. It does not strip dates or merge generations automatically. DeepSeek's priced aliases retain the served 1017/0813 version; an older unversioned SWE-rebench record stays separate. Provider spelling variants are normalized without changing model identities.

`research/*.json` retain original numeric fields and detailed provenance. `src/lib/snapshot.json` holds the app's normalized records, per-result URLs, metadata and source catalog. Zod validates URLs, numeric values, unique IDs, model/benchmark references and cost/time context. Regression tests cover the cost denominator, missingness, configuration matching, price thresholds and scheduled rates.

## Refresh procedure

The commands, expected output and the steps after a change to the model list are in [Updating the data](updating.md#benchmarks-prices-reports-and-the-app-guide). In short:

1. Reopen each relevant primary source. Record a new checked date; preserve evaluation dates and versions.
2. Update the reviewed JSON in `research/`, preserving units, uncertainty, cost basis and exact configuration.
3. Review model-name joins explicitly; an API alias can change its served release.
4. Run `npm run data:build`, `npm run records:build`, `npm test`, `npm run build`, and formatting checks.
5. Check an affected brief, the benchmark page, selected configurations and source links, at desktop and phone width, before committing.

No background refresh, API keys or accounts are configured for the benchmark and guide data. Several data APIs require credentials or attribution; access notes are in the in-app source catalog. A future live integration must preserve the same provenance and version rules.

Detailed source notes: [benchmarks](../research/benchmarks.md), [pricing](../research/pricing.md), [reports and creative benchmarks](../research/reports.md).

[`research/jobs.json`](../research/jobs.json) holds the job list as data. `status` is `approved` for the list in use (version 2, approved on 23 November 2026). Each job has an `id`, a `label`, an optional `parent` (one level only), the `benchmarks` that set its order in priority order and the App guide task it maps to (`guideTask`). A job measured differently per surface also has `bySurface`: for each surface, the benchmarks that order it there, the first surface being the default. A general index (the Epoch Capabilities Index) may not be listed: it orders no job. A job with no benchmarks has no measure; it never takes its parent's.

The 13 jobs: **Write or change code** (`code`) with four sub-jobs, Find and fix a fault (`debug`), Review code or a change (`review`), Plan or design software (`plan`) and Build a web page or app interface (`interface`); Research with web search (`research`); Analyse documents or data you supply (`documents`); Extract or classify data (`extraction`); Write, edit or translate (`writing`); Maths, science and logic problems (`maths`); Everyday questions and advice (`chat`); Read images, scans, audio or video (`read-media`); Make or edit images and video (`make-images`). A record carries one job, and a sub-job counts toward its parent. Review, plan and extraction have no measure. Write or change code is ordered by Terminal-Bench for coding agents and by Text Arena coding for chat.

- **Crosswalk.** `crosswalk` maps each source's own labels to a job: Hacker News task, Hacker News theme (used only when the task maps to no job, first listed theme first), a published report by its id (`report`) and otherwise by its category (`report-category`), benchmark id, LMArena leaderboard (`arena-leaderboard`, as `<config>/<category>`), Epoch run file (`epoch-run`), OpenRouter task tag (`openrouter-tag`), the people review's job (`review-job`) and a restricted benchmark's category (`benchmark-category`), each an exact label. Each entry has a `fit`: `direct` (the same task), `loose` (an overlapping one, with a `note` saying how) or `none` (no job). The build checks that `none` is given exactly when the entry gives no job.
- **Keyword rules.** `keywords` can hold rules that refine or fill in a label's job; the first rule whose pattern matches and whose `within` list holds the label's job wins (`null` stands for no job). The approved list has none.
- **Replacements.** Stored records keep the job they were reviewed with: the Hacker News tasks are the earlier list's, while the people review has labelled with the approved list since 24 November 2026, so its labels map directly (`review-job`). `replaces` maps each earlier job id to its new job, or, for a job that was split or became a field, to no job with the jobs it was split into (`into`) or the field it sets (`setting` or `run`), and keeps the earlier `label` for notices. Merged: coding, refactor and tests into `code`; bug-fix to `debug`; planning to `plan`; analysis to `documents`. Split: reasoning (into maths and everyday questions) and images (into read media and make images). Became fields: local (setting local), agents (run unattended), delegation (run parallel).
- **Records that need reading.** A record whose label leads to an earlier job that was split or became a field gets no job by rule and is never given one by guess: its `how` is `pending` and `via` keeps the label. The build counts these apart from records with no job, by the earlier job, and the Data page shows both per source. The next review with the new list gives them a job. On 24 November 2026, before the people review with the new list, they were 1,776 use records and 9,456 Hacker News comments, from hard reasoning and maths, images and vision, long agent runs, parallel agents and delegation, and local or private use; after it, only the Hacker News comments.
- **Fields.** `fields` sets `setting` and `run` by rule: from `replaces` (above), from the Hacker News themes `local-use` (setting local) and `agentic-work` (run unattended) whatever the task, and from the surface (a local runner sets setting local). `surface` derives a record's surface from its `tool`: lower-case words per surface, matched as whole words, the first surface that matches wins. The people review labels `setting` and `run` itself when a passage states them, and the surface rule fills setting local only where the review left it blank. Nothing sets them on Hacker News records until a review labels them.
- **Tags.** `tags` holds rules that mark records without giving a job: `drawing-test` matches a pelican or SVG drawing test in a use record's task or a Hacker News claim. The Model page shows tagged records; a tag never counts toward a job.
- **Guide.** `guide` links each App guide task to the brief of the job whose `guideTask` names it, or to none with a note. A link whose fit is `loose` carries a note (Hard reasoning links loosely to maths); Parallel work links to none, as it is a way of running.

Each table has its own `version`. Restricted benchmarks are not in the file: their job comes from the category in `.local/restricted/research.json` through `benchmark-category`, where `reasoning` and `agents` give no job under the approved list.

Old addresses with an earlier job id (`#/brief/<id>`, `?job=<id>`) land on the job that replaced it, or, for a job that was split or became a field, on the chooser (or the page with all jobs) with a one-line notice; `npm run search -- --job <id>` reads old ids the same way (`src/lib/job-rules.ts`).

`npm run records:build` reads `src/lib/snapshot.json`, the imported LMArena and Epoch files, the OpenRouter usage file, the App guide and the job file, Hacker News from the served run in `.local/hn/` when a checkpoint exists, else from the published export in `dist/`, and the people review in `.local/people/` when it exists. It never writes under `.local/` and never reads `.local/restricted/`. Reading the checkpoint uses a read-only SQLite connection, as the export does, which keeps SQLite's shared-memory index beside the database up to date. It writes `build/records/core.json` (ignored): the sources' dates and counts (`sources`), the job list with the restricted categories' jobs and the App guide table (`jobs.list`, `jobs.categories`, `jobs.guide`), models, product lines, benchmarks with their scale, source, row count and attribution, measured records, Hacker News stance totals and label counts per target, job and month (`crowd.counts`, per theme in `crowd.themes`, the comment ids per job in `crowd.comments`, again per setting and run other than the default in `crowd.cells`, the comment ids of tagged comments in `crowd.tags` and of comments that need reading in `crowd.pending`), stated preferences with their setting and run, coverage per job and source with the records that need reading apart (`coverage.pending`), which it also prints, and the OpenRouter usage block, which changes none of the others. `core.json` names no person and holds no named record or count; `namedBehindSignIn` says whether named records were built. With a people review it also writes `build/records/named-private.json` (ignored, served only behind sign-in): the use records and method advice with their quotes, and the people list. It writes the word-search index too: `build/records/search/`, the public static files of measured records and Hacker News labels, and `build/records/search-local.sqlite`, which adds the use records and method advice with their quotes for `npm run search` on this machine and is never published (see [Search](search.md)). Its rules are in the [people pipeline](people-pipeline.md#the-records-build). A job id that is neither in the list nor in `replaces`, a source label the crosswalk does not list, a benchmark, parent or App guide task that does not exist, an imported file without `checkedAt` or with a model that is not in the snapshot, or a record that fails the schema stops the build and lists the records concerned.

Options: `--hn-root <checkout>` reads `.local/hn/` or `dist/` from another checkout (for example from a worktree); `--hn-source checkpoint` or `export` chooses one; `--people-root <checkout>` reads `.local/people/` from another checkout (default: the `--hn-root` one); `--jobs`, `--out`, `--named-out`, `--search-out` and `--search-local` change the job file and the outputs.

## LMArena and Epoch runs

Two measured sources are imported by script rather than read by hand. Each importer downloads its source into a new folder under `.local/imports/`, checks the licence and the format, keeps only the results whose model name has an exact entry in its alias table, and writes one reviewed file. The update steps are in [Updating the data](updating.md#lmarena-and-epoch-runs).

| File                       | Source                                                                                                                                                                                                                                          | Licence   | Records                                                                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `research/lmarena.json`    | [Arena leaderboard dataset](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset) on Hugging Face, `latest` split, read through the datasets server. arena.ai pages are not used.                                                     | CC BY 4.0 | `la:`, `src: arena`: rating, confidence bounds, votes (Agent Arena: observations, sessions and median cost per task), rank and publish date |
| `research/epoch-runs.json` | [Epoch AI's benchmark data](https://epoch.ai/benchmarks/use-this-data), the ZIP at `epoch.ai/data/benchmark_data.zip`, read without extracting. Only Epoch's own runs; the `_external` files keep their sources' licences and are not imported. | CC BY 4.0 | `ep:`, `src: benchmark`: best score across scorers, mean score, standard error, run date, log link                                          |

Each file states its source, licence and attribution line, the date it was fetched (`fetchedAt`) and the date a person reviewed it (`checkedAt`), and lists the leaderboards or run files read with what each measures, its unit, the rows it had and the results kept. `scripts/import_lmarena.py` and `scripts/import_epoch.py` hold the list of leaderboards and files and their "what it measures" text; a new one also needs a crosswalk entry in `research/jobs.json`. The attribution lines are shown on the Data page from `src/lib/attribution.ts`, and a test checks that they match the files.

Model names are matched by `research/aliases/lmarena.json` and `research/aliases/epoch.json`, each with its rule. Only the effort setting and harness of an LMArena name (`Claude Fable 5.2 (xHigh)`, `GPT-5.6 Sol (xHigh, Codex Harness)`) and the reasoning-setting suffix of an Epoch model version (`gemini-4-neon_xhigh`) are read as settings; the rest of the name must be an exact key. Dates, versions, sizes, quantisations, provider suffixes and resolutions are never taken out, so a different release stays out. An alias can only name a model id already in the snapshot: importers never add a model, and a test checks that importing leaves `src/lib/snapshot.json` unchanged. A name listed twice on one leaderboard cannot be matched.

Limits:

- **Arena ratings are preference votes, not a pass rate.** A rating says which answer visitors preferred in blind side-by-side votes on their own prompts within one category, relative to the other models on the same leaderboard and publish date. It does not measure correctness, and votes reward style and length; style control, on for the text, vision, document and search leaderboards used, reduces that but does not remove it. Ratings from different leaderboards or dates do not compare, and they never share a column or an axis with percentages. Agent Arena gives an inverse-propensity score from real agent sessions, not a fixed task set. Text · longer query is a proxy for long inputs, not a document test. The arena changed its rating method several times, so older publications are not one series.
- **Epoch runs** state the reasoning setting in the model version; `unknown` or no suffix is recorded as not stated. The interval is 1.96 standard errors either side of the score. The files do not give question counts. Several settings of one model give several records.
- Leaderboards and run files that no job covers, and the results of models outside the model list, are not imported.

## OpenRouter usage

`research/openrouter-usage.json` holds how much public [OpenRouter](https://openrouter.ai/rankings) traffic each model carries. It comes from two calls to the OpenRouter Data API, which needs a key, made by `scripts/import_openrouter.py` (update steps in [Updating the data](updating.md#openrouter-usage)). The data is licensed CC BY 4.0, must carry the citation `Source: OpenRouter (openrouter.ai/rankings), as of <as_of>.` with `Licensed under CC BY 4.0.`, and is not to be re-served as a competing free API.

| Block       | Endpoint                                 | Holds                                                                                                                                                                                                                  |
| ----------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tokens30d` | `/api/v1/datasets/rankings-daily`        | Tokens per model over 30 days, summed from the daily top 50 public models; each model's share of all public tokens (the `other` row of models outside the top 50 included) and the number of days it was in the top 50 |
| `tasks7d`   | `/api/v1/classifications/task?window=7d` | Each task tag's share of classified requests over the trailing 7 days, and its top 10 models by share of that tag's requests. The classification is sampled and gives no absolute volumes                              |

Each block keeps the `meta` block it was published with (`as_of`, the period), its own citation and the endpoint, because figures can be restated as the data refreshes. Routes are matched by `research/aliases/openrouter.json`: exact keys only, after taking out a `:free` suffix, which serves the same weights. Unmatched routes are left out of the token shares; in a tag's top list they keep their place with no model id, so the ranks stay as published. The importer never adds a model.

Usage is not a measured result and not evidence of quality. Volume follows price, free routes, default settings in apps and a few heavy users; one app can move a model's share, and the top of a task list is often the cheapest models. Tokens are counted by each provider's own tokenizer, so totals do not compare exactly across providers. Private, zero-retention and direct-provider traffic is absent. So usage orders nothing: it is not a record, never enters a score, an order or a count of results, and never fills in a job that has no measure. `npm run records:build` writes it to its own `usage` block in `core.json`, with each tag's job from the `openrouter-tag` crosswalk; a model outside a tag's top 10 has no figure there, which is not zero.

## Hacker News processing

The local HN pipeline supersedes the 49-comment collection as the route for broad coverage. It streams the selected six-month archive portions and recent mirror records, reconciles in-range gaps against the official API, and records processed counts. It does not use relevance-ranked top-20 search results as its corpus. The current version, `hn-thread-v1`, queues comments that name a model and every in-window comment in a thread whose story title names one, then has a model review each comment with its replied-to text and story title. The model is a local one on a loopback endpoint or a Claude model through the Anthropic API, and reads scrubbed public text; raw text and author fields are never written to disk. The checkpoint stores derived labels, scrubbed story titles and one-sentence claims written by the model, and exposes failures separately. The run served since 19 November 2026 was reviewed by Claude Haiku 5.5 through the API. It replaced the previous analysis, whose classifier read only masked context around detected model mentions. Full details, verification and refresh boundaries are in [pipeline instructions](hn-pipeline.md) and [archive checks](hn-archive-check.md).

The Cloudflare Pages build exports the served run's summary and the metadata of every comment with at least one valid assessment, from one SQLite read transaction. Its counts use distinct comment records rather than cumulative source-partition counters. For a run made by `hn-thread-v1`, the export also includes the story ID, parent ID, task, claim, themes and preferences of each listed comment, and the scrubbed titles of their stories. The previous analysis gains the story ID, parent ID and scrubbed story titles once the `context` command has filled them in, so an export made after that includes them too. The export refuses a run whose classifier differs from the [quality record](../research/hn-classifier-check.json), which describes the served run's classifier. The comments are written as several files, because Cloudflare Pages accepts at most 25 MiB for one. The served run was published on 19 November 2026. The in-app reader retrieves public comment text on demand, without adding bodies or author fields to the published files. The publication timestamp identifies the hosted snapshot; it does not update automatically when local processing continues.
