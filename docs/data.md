## Pricing

23 models have official standard API token rates: seven OpenAI, five Anthropic, six Google, two DeepSeek and three xAI. Rates are USD per million tokens; they do not imply a per-project cost. Long-context tiers and DeepSeek peak/off-peak conditions are recorded. Gemini Carbon/Argon promotional rates and the announced 1 December change are retained.

98 model identities cover these price records plus benchmark-only and report-only models, including older releases and image models. The remaining identities have no verified price record in this snapshot. Missing values are never filled by analogy. Provider positioning is labelled as a provider description.

## Identity and normalization

Each model's status (current, previous or preview) feeds the Board's "Current models only" filter. Priced models take it from `research/pricing.json` and the others from `research/model-status.json`, which gives a reason for each; a model is previous when a newer model of its line is in the data or its provider names a replacement. Ten models, mostly image models, have no status because the data does not settle it.

The build script joins exact reviewed names and a small explicit spelling-alias table. It does not strip dates or merge generations automatically. DeepSeek's priced aliases retain the served 1017/0813 version; an older unversioned SWE-rebench record stays separate. Provider spelling variants are normalized without changing model identities.

`research/*.json` retain original numeric fields and detailed provenance. `src/lib/snapshot.json` holds the app's normalized records, per-result URLs, metadata and source catalog. Zod validates URLs, numeric values, unique IDs, model/benchmark references and cost/time context. Regression tests cover the cost denominator, missingness, configuration matching, price thresholds and scheduled rates.

## Refresh procedure

The commands, expected output and the steps after a change to the model list are in [Updating the data](updating.md#benchmarks-prices-reports-and-the-app-guide). In short:

1. Reopen each relevant primary source. Record a new checked date; preserve evaluation dates and versions.
2. Update the reviewed JSON in `research/`, preserving units, uncertainty, cost basis and exact configuration.
3. Review model-name joins explicitly; an API alias can change its served release.
4. Run `npm run data:build`, `npm test`, `npm run build`, and formatting checks.
5. Check the chart, selected configurations, source links and mobile comparison before committing.

No background refresh, API keys or accounts are configured for the benchmark and guide data. Several data APIs require credentials or attribution; access notes are in the in-app source catalog. A future live integration must preserve the same provenance and version rules.

Detailed source notes: [benchmarks](../research/benchmarks.md), [pricing](../research/pricing.md), [reports and creative benchmarks](../research/reports.md).

## Shared records and the job list

The app does not read these yet. Every source becomes the same record, defined twice with the same rules: `src/lib/records.ts` (Zod) and `scripts/records_schema.py` (for the build). `tests/records.test.ts` checks that both accept and reject the same fixtures in `tests/fixtures/`.

| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                             | Stable across builds: `hn:<item id>`, `bm:<result id>`, `rp:<report id>`, `la:<config>/<category>/<model as listed, lower case, each run of characters other than letters, digits and dots as one hyphen>/<publish date>`, `ep:<file>/<model version>`; `ur:` and `ma:` are reserved for use and advice records |
| `cls`, `src`                     | `measured` (`benchmark`, `arena`, `report`), `named` (`use`, `advice`) or `crowd` (`hn`)                                                                                                                                                                                                                        |
| `keys`                           | Targets, each with a stance: `model\|<id>`, `line\|<name>` (a product line only), `version\|<name>` (an exact version not in the model list), `tool\|<name>`                                                                                                                                                    |
| `job`, `how`, `via`              | Job id or empty; how it was assigned (`label`, `keywords`, `review`); the label or rule that assigned it                                                                                                                                                                                                        |
| `stance`                         | `positive`, `critical`, `mixed` or `neutral`                                                                                                                                                                                                                                                                    |
| `text`, `quote`                  | One-sentence summary; the source's own words, kept on named records only                                                                                                                                                                                                                                        |
| `cond`, `tool`, `effort`         | Conditions, app or coding agent, and effort setting where stated                                                                                                                                                                                                                                                |
| `setting`, `run`, `surface`      | `local` or `hosted`; `interactive`, `unattended` or `parallel`; `surface` is derived from `tool` (`coding-agent`, `chat-app`, `api`, `local-runner`), never labelled                                                                                                                                            |
| `date`, `checked`                | Source date; date the record was read against its source by a person (benchmark results and reports: the snapshot's checked date; LMArena and Epoch: the imported file's `checkedAt`)                                                                                                                           |
| `person`, `url`, `title`, `kind` | Person or outlet (named records only), source link, source title, source-specific kind                                                                                                                                                                                                                          |
| `x`                              | Source extras, such as the benchmark id, score, interval, trials and cost, or Hacker News themes                                                                                                                                                                                                                |

[`research/jobs.json`](../research/jobs.json) holds the job list as data. `status` is `draft` until the owner approves a list. Each job has an `id`, a `label`, an optional `parent` (one level only), the `benchmarks` that set its order in priority order and the App guide task it maps to (`guideTask`). `crosswalk` maps each source's own labels to a job: Hacker News task, Hacker News theme (used only when the task maps to no job, first listed theme first), report category, benchmark id, LMArena leaderboard (`arena-leaderboard`, as `<config>/<category>`) and Epoch run file (`epoch-run`), each an exact label. `keywords` holds the rules that refine or fill in a label's job; the first rule whose pattern matches and whose `within` list holds the label's job wins (`null` stands for no job). `surface` maps tool names to a surface. `replaces` maps an old job id to its new job (or `null`) and, where the old job became a field, its `setting` or `run`. Each table has its own `version`. Restricted benchmarks are not in the file.

`npm run records:build` reads `src/lib/snapshot.json`, the imported LMArena and Epoch files, the App guide and the job file, and Hacker News from the served run in `.local/hn/` when a checkpoint exists, else from the published export in `dist/`. It never writes under `.local/` and never reads `.local/restricted/`. Reading the checkpoint uses a read-only SQLite connection, as the export does, which keeps SQLite's shared-memory index beside the database up to date. It writes `build/records/core.json` (ignored): models, product lines, jobs, benchmarks, measured records, Hacker News label counts per target, job and month, stated preferences, and coverage per job and source, which it also prints. A job id that is neither in the list nor in `replaces`, a source label the crosswalk does not list, a benchmark, parent or App guide task that does not exist, an imported file without `checkedAt` or with a model that is not in the snapshot, or a record that fails the schema stops the build and lists the records concerned.

Options: `--hn-root <checkout>` reads `.local/hn/` or `dist/` from another checkout (for example from a worktree); `--hn-source checkpoint` or `export` chooses one; `--jobs` and `--out` change the job file and the output.

## LMArena and Epoch runs

Two measured sources are imported by script rather than read by hand. Each importer downloads its source into a new folder under `.local/imports/`, checks the licence and the format, keeps only the results whose model name has an exact entry in its alias table, and writes one reviewed file. The update steps are in [Updating the data](updating.md#lmarena-and-epoch-runs).

| File                       | Source                                                                                                                                                                                                                                          | Licence   | Records                                                                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `research/lmarena.json`    | [Arena leaderboard dataset](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset) on Hugging Face, `latest` split, read through the datasets server. arena.ai pages are not used.                                                     | CC BY 4.0 | `la:`, `src: arena`: rating, confidence bounds, votes (Agent Arena: observations, sessions and median cost per task), rank and publish date |
| `research/epoch-runs.json` | [Epoch AI's benchmark data](https://epoch.ai/benchmarks/use-this-data), the ZIP at `epoch.ai/data/benchmark_data.zip`, read without extracting. Only Epoch's own runs; the `_external` files keep their sources' licences and are not imported. | CC BY 4.0 | `ep:`, `src: benchmark`: best score across scorers, mean score, standard error, run date, log link                                          |

Each file states its source, licence and attribution line, the date it was fetched (`fetchedAt`) and the date a person reviewed it (`checkedAt`), and lists the leaderboards or run files read with what each measures, its unit, the rows it had and the results kept. `scripts/import_lmarena.py` and `scripts/import_epoch.py` hold the list of leaderboards and files and their "what it measures" text; a new one also needs a crosswalk entry in `research/jobs.json`. The attribution lines are shown on the Data page from `src/lib/attribution.ts`, and a test checks that they match the files.

Model names are matched by `research/aliases/lmarena.json` and `research/aliases/epoch.json`, each with its rule. Only the effort setting and harness of an LMArena name (`Claude Fable 5.2 (xHigh)`, `GPT-5.6 Sol (xHigh, Codex Harness)`) and the reasoning-setting suffix of an Epoch model version (`gemini-4-neon_xhigh`) are read as settings; the rest of the name must be an exact key. Dates, versions, sizes, quantisations, provider suffixes and resolutions are never taken out, so a different release stays out. An alias can only name a model id already in the snapshot: importers never add a model, and a test checks that importing leaves `src/lib/snapshot.json` unchanged. A name listed twice on one leaderboard cannot be matched.

Limits:

- **Arena ratings are preference votes, not a pass rate.** A rating says which answer visitors preferred in blind side-by-side votes on their own prompts within one category, relative to the other models on the same leaderboard and publish date. It does not measure correctness, and votes reward style and length; style control, on for the text, vision, document and search leaderboards used, reduces that but does not remove it. Ratings from different leaderboards or dates do not compare, and they never share a column or an axis with percentages. Agent Arena gives an inverse-propensity score from real agent sessions, not a fixed task set. Text · longer query is a proxy for long inputs, not a document test. The arena changed its rating method several times, so older publications are not one series.
- **Epoch runs** state the reasoning setting in the model version; `unknown` or no suffix is recorded as not stated. The interval is 1.96 standard errors either side of the score. The files do not give question counts. Several settings of one model give several records.
- Leaderboards and run files that no job covers, and the results of models outside the model list, are not imported.

## Hacker News feedback

The separate `research/hn-sentiment.json` snapshot contains 49 AI-assessed comments from 42 discussions, selected from 348 candidates returned by 20 model-name queries for 20 May–16 November 2026. Seventeen queried model identities have exact-version feedback. Gemini 4 Carbon and the dated DeepSeek releases remain explicit evidence gaps; unversioned DeepSeek comments are family evidence only.

All selected comment IDs, timestamps, visibility states and parent chains were checked against the official API. Sentiment, topic labels and paraphrases are AI inferences without independent human validation. The sample is relevance-ranked and selectively reviewed, with a five-comment discussion cap; it cannot establish population percentages or a universal model ranking.

`src/lib/community.ts` validates strict fields, exact model references, canonical UTC timestamps, permalinks, deduplication, the collection window and declared counts. Filtered counts use distinct comments and discussions after narrowing each assessment to its target. The downloadable data excludes account fields, raw comment bodies and quotations.

Eight additional public APIs, GitHub ingestion repositories and downloadable/hosted datasets are catalogued in [HN sources](../research/hn-sources.md). Current collection uses Algolia discovery and official API verification. Historical archives have separate freshness and access limitations.

The read-only `scripts/collect-hn.py` provides discovery metadata and official-item verification; it never overwrites labels or refreshes sentiment automatically. Verification does not detect changes to wording. See [HN methodology and refresh](../research/hn-sentiment.md).

## arXiv papers

The Papers page lists arXiv papers whose title or abstract names a tracked model or family, harvested from arXiv's OAI-PMH metadata for the same six-month window. Matching reads only the title and abstract, so papers that mention a model in passing are included and models named only in the body are missed. Abstract labels are produced by a local model. On 18 November 2026 they existed for 1,382 of the 1,383 papers that name an exact tracked model, and papers harvested later have none until labelling is run again; papers that name only a family are unlabelled. For papers labelled as evaluations, the same model also records the area and task tested, the named models the abstract reports as best or as behind the best, and a one-sentence finding. 413 of the 414 evaluation papers have a result. The published snapshot carries titles, identifiers, dates, categories, matched targets, labels and results; abstracts stay local. See [arXiv pipeline instructions](arxiv-pipeline.md).

## Reviewed theme sample

`research/hn-themes-sample.json` holds 217 AI-reviewed claims from the 50 most recent collected comments for each of six models (Opus 5.5, Fable 5.2, Sonnet 5.5, Astra, 6.1 Sol and Gemini 4 Argon), fetched 17 November 2026. Each entry has a stance, a one-sentence paraphrase, one to three themes from a fixed list of 18, the task and tool where stated, and any explicit comparison. 83 of the 300 comment-model pairs only mention the model in passing and are counted, not summarised. It is a single AI pass with no human validation, recency-biased, and far too small for rates. It was made to show what a theme-level pass over the full collection would add. The thread pipeline now makes that pass, and the app shows the sample only with an analysis that has no themes. The local `hn-thread-v1` pipeline uses 17 of these themes (all but `other`) plus `local-use`, `policy` and `release`. The sample contains no account fields or quotations.

## Expert articles

The catalog uses archived first-party blogs and newsletters, including team-blog articles with a supported byline. It keeps the original title, publication date and canonical link. The review excludes replies, interviews, reposts and records with unresolved article type, authorship or date. Collection coverage varies by source. The catalog is stored as a private input to the Pages Function at `/api/expert-articles`.

## Hacker News processing

The local HN pipeline supersedes the 49-comment collection as the route for broad coverage. It streams the selected six-month archive portions and recent mirror records, reconciles in-range gaps against the official API, and records processed counts. It does not use relevance-ranked top-20 search results as its corpus. The current version, `hn-thread-v1`, queues comments that name a model and every in-window comment in a thread whose story title names one, then has a model review each comment with its replied-to text and story title. The model is a local one on a loopback endpoint or a Claude model through the Anthropic API, and reads scrubbed public text; raw text and author fields are never written to disk. The checkpoint stores derived labels, scrubbed story titles and one-sentence claims written by the model, and exposes failures separately. The run served since 19 November 2026 was reviewed by Claude Haiku 5.5 through the API. It replaced the previous analysis, whose classifier read only masked context around detected model mentions. Full details, verification and refresh boundaries are in [pipeline instructions](hn-pipeline.md) and [archive checks](hn-archive-check.md).

The Cloudflare Pages build exports the served run's summary and the metadata of every comment with at least one valid assessment, from one SQLite read transaction. Its counts use distinct comment records rather than cumulative source-partition counters. For a run made by `hn-thread-v1`, the export also includes the story ID, parent ID, task, claim, themes and preferences of each listed comment, and the scrubbed titles of their stories. The previous analysis gains the story ID, parent ID and scrubbed story titles once the `context` command has filled them in, so an export made after that includes them too. The export refuses a run whose classifier differs from the [quality record](../research/hn-classifier-check.json), which describes the served run's classifier. The comments are written as several files, because Cloudflare Pages accepts at most 25 MiB for one. The served run was published on 19 November 2026. The in-app reader retrieves public comment text on demand, without adding bodies or author fields to the published files. The publication timestamp identifies the hosted snapshot; it does not update automatically when local processing continues.
